# EduHub 요구사항

## 개요
임직원이 사내 교육과정을 조회·신청하고, 정원이 차면 대기자로 등록되는 시스템.
- 사용자: 임직원(수강생), 교육 담당자(관리자)

## 기술 스택
- 백엔드: Java 21, Spring Boot 3, Spring Data JPA, Flyway, springdoc-openapi, PostgreSQL
- 프론트엔드: React 18 + TypeScript, Module Federation(shell, course-mfe, enrollment-mfe), MUI, Axios
- 빌드: Gradle(Kotlin DSL), npm workspaces

## 기능 요구사항 (무엇을 하는가)

| ID | 요구사항 | 사용자 | 우선순위 | 주차 |
|---|---|---|---|---|
| FR-01 | 교육과정 목록을 조회하고 제목·분류로 검색한다 (페이지 단위) | 임직원 | 필수 | 2 |
| FR-02 | 과정 상세와 회차(일정, 장소, 정원, 남은 자리)를 조회한다 | 임직원 | 필수 | 2 |
| FR-03 | 관리자는 과정과 회차를 등록·수정·종료한다 | 관리자 | 필수 | 2 |
| FR-04 | 회차에 수강 신청한다. 같은 회차에 중복 신청할 수 없다 | 임직원 | 필수 | 3 |
| FR-05 | 정원이 차면 대기자로 등록되고 대기 순번을 알려 준다 | 임직원 | 필수 | 3 |
| FR-06 | 신청을 취소하면 대기 1순위가 자동으로 신청 확정된다 | 임직원 | 필수 | 3 |
| FR-07 | 내 신청 내역(확정, 대기, 취소, 수료)을 조회한다 | 임직원 | 필수 | 4 |
| FR-08 | 관리자는 회차별 신청자·대기자 명단을 보고 수료 처리한다 | 관리자 | 보통 | 4 |
| FR-09 | 신청 확정·대기 승급 시 알림을 남긴다 (처음에는 로그·DB 기록) | 임직원 | 선택 | 5 |

## 비기능 요구사항 (얼마나 잘, 어떤 제약 아래서)
| ID | 분류 | 요구사항 | 확인 방법 |
|---|---|---|---|
| NFR-01 | **정합성** | 동시에 100명이 마지막 1자리에 신청해도 정원을 넘지 않는다 | 동시성 테스트 |
| NFR-02 | **성능** | 과정 목록 API는 데이터 1만 건에서 응답 300ms 이내, N+1 쿼리 없음 | 쿼리 로그, 성능 테스트 |
| NFR-03 | **보안** | 로그인한 사용자만 신청 가능, 본인 신청만 취소 가능, 비밀 정보는 저장소에 두지 않음 | 테스트, 비밀 검사 |
| NFR-04 | **API 계약** | 모든 API는 OpenAPI 문서가 있고, 프론트 클라이언트는 스펙에서 생성한다 | Swagger UI, 생성 스크립트 |
| NFR-05 | **품질** | 서비스 계층 테스트 커버리지 70% 이상, CI에서 빌드·테스트·포맷 검사 | CI 결과 |
| NFR-06 | **운영성** | 개발·테스트·운영 설정 분리, 사람이 직접 실행할 수 있는 빌드·배포·롤백 절차 문서 | 런북, 핫픽스 훈련 |
| NFR-07 | **유지보수성** | 도메인별 패키지(course, enrollment), 계층 규칙 준수, 화면은 MFE로 분리 | 리뷰, 아키텍처 테스트 |
| NFR-08 | **이해도** | 팀원 누구나 AI 없이 구조와 핵심 파일의 역할을 설명할 수 있다 | 발표 시 확인 |

> 💡 NFR-08은 일반 프로젝트에는 없는 이 과정만의 요구사항입니다. 1회차의 **"시스템의 주인은 개발자"** 원칙을 평가 항목으로 만든 것입니다.

## 결정 사항

| ID | 관련 | 결정 | 이유 |
|---|---|---|---|
| D-01 | FR-03, FR-05, FR-06 | **회차 상태는 모집 중 → 모집 마감 → 교육 완료.** FR-03의 "종료"는 모집 마감이다. 신규 신청·대기만 막고 기존 확정·대기는 유지한다. 회차 시작 시각이 되면 자동으로 모집 마감되고, 남은 대기 신청은 취소(사유: 회차 시작)된다. "정원 마감"은 상태가 아니라 남은 자리 0으로 계산한다. | 종료로 이미 확정된 사람이 사라지면 안 된다. 상태를 늘리지 않아 단순하다 |
| D-02 | FR-03, FR-06 | **정원을 늘리면 늘어난 자리만큼 대기 순번대로 자동 확정한다.** 정원은 현재 확정 인원보다 작게 줄일 수 없다. 회차·과정은 신청이 하나라도 있으면 삭제하지 않는다. 과정 종료는 새 회차 등록과 목록 노출만 막는다 | 자동 승급 규칙을 "자리가 생기면 승급"으로 통일한다. 확정된 사람을 강제로 밀어내지 않는다 |
| D-03 | FR-04 | **한 사람은 같은 과정에 유효 신청(확정 또는 대기)을 1건만 가질 수 있다.** 다른 회차라도 마찬가지다. 취소하면 다시 신청할 수 있고, 새 신청으로 처리된다(대기면 맨 뒤). 수료한 과정은 다시 신청할 수 없다 | 한 사람이 여러 회차 자리를 차지해 다른 사람의 기회를 막는 일을 막는다 |
| D-04 | FR-05, FR-06, FR-09 | **확정·대기 모두 회차 시작 전까지 본인이 취소할 수 있다.** 대기 순번은 저장하지 않고 신청 시각 순으로 계산한다. 그래서 대기자가 취소하면 뒤 순번이 자동으로 당겨진다. 확정자가 취소하면 같은 트랜잭션에서 대기 1순위를 확정한다. 승급은 수락 절차 없이 자동이다. 신청에 확정 시각과 "대기에서 승급" 여부를 기록해 FR-07 내역에 바로 보이게 한다(FR-09 알림은 5주차에 이 기록 위에 붙인다). 순번은 신청 응답과 내역 조회 때 그 시점 값을 보여 준다 | 순번을 저장하면 취소 때마다 재정렬해야 하고 동시성 문제가 생긴다(NFR-01). 알림 없이도 승급 사실을 확인할 수 있다 |
| D-05 | FR-07, FR-08 | **수료 처리는 확정 신청만, 회차가 교육 완료된 뒤에만 한다.** 관리자는 확정 신청을 수료 또는 **미수료**로 처리한다. FR-07의 상태 목록에 미수료를 추가한다 | 불참자를 "확정"으로 남기면 이수 기록이 부정확해진다 |

**신청 상태 전이 (결정 반영)**

| 현재 | 이벤트 | 다음 |
|---|---|---|
| (없음) | 신청, 남은 자리 있음 | 확정 |
| (없음) | 신청, 정원 참 | 대기 |
| 대기 | 확정 취소·정원 증가로 자리 생김, 1순위 | 확정 (승급 기록) |
| 확정 / 대기 | 회차 시작 전 본인 취소 | 취소 |
| 대기 | 회차 시작 | 취소 (사유: 회차 시작) |
| 확정 | 교육 완료 후 관리자 처리 | 수료 / 미수료 |
